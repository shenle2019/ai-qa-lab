# 接口自动化高频面试题（带答案）

这页收的是面试里反复出现的题，答案按「能直接说出口」的长度写。每题都给了追问方向，面试官往下问时不至于卡住。

## 一、基础与协议

### 1. 接口测试到底在测什么？

测「契约」：请求该怎么发、响应该长什么样、边界和异常怎么处理。具体拆成七块——方法、路径、参数位置、请求头、状态码、响应体结构、错误码。断言落在这七块上，才算测了接口，而不只是「调通了」。

> 追问：那接口测试和集成测试的区别？——接口测试聚焦单个契约，集成测试关注多个服务串起来后的行为和数据一致性。

### 2. 401 和 403 怎么区分？

401 是「没认证」：没带 token、token 过期，客户端应该去登录；请求签名校验不通过（HMAC / AWS 那类）常按文档给 403，别一律当 401。403 是「认证过了但没权限」：普通用户访问管理接口。测试时 401 用「不带 token / 过期 token」，403 用「低权限账号访问高权限接口」。

### 3. PUT 和 PATCH 的区别，测试要注意什么？

PUT 是整体替换：没传的字段会被置空或删掉，所以测试要验「只传部分字段后，其余字段是否被清空」。PATCH 是局部更新，只改传入的字段。两个都要测非法字段、类型错误；「资源不存在」按文档判——PATCH 通常 404，PUT 允许「不存在就创建」（201/204），别写死成 404。

### 4. 幂等怎么测？

看有没有幂等键。有键：同一个键连发两次，按文档断言第二次**重放首次结果**（首次 201，重放通常还是 201；并发没跑完时也可能 409），body 里的 id 与第一次相同、库里只有一条。没键：重复提交按业务规则处理，通常第二次返回 409 或返回同一结果，要按文档断言。

### 5. 一个创建接口返回 200 而不是 201，算 bug 吗？

先看契约。REST 惯例是 201 + `Location`，但如果接口文档明确写 200，就按 200 断言——同时把「与惯例不一致」提出来，因为它影响客户端缓存（201 默认不被缓存）和消费方的分支处理；幂等由请求方法和幂等键决定，跟状态码无关。判断标准永远是文档，不是个人习惯。

## 二、用例设计

### 6. 给你一个接口，你怎么设计用例？

按维度铺：参数（必填、类型、长度、枚举、位置）、鉴权（无 token、过期、越权）、状态（重复提交、并发、非法状态流转）、数据（分页边界、空集合、超长、特殊字符）、协议（方法、Content-Type、状态码、响应头）。铺完画成「接口 × 维度」矩阵，空格就是缺口。

### 7. 边界值为什么比中间值更重要？

bug 集中在边界：0、1、最大值、超一位、空串、null。中间值大多走同一条代码路径，测十个和测一个没区别。分页就测第 1 页、最后一页、越界页；金额就测 0、0.01、上限、上限 + 0.01。

### 8. 用例之间能依赖顺序吗？

不能。依赖顺序意味着单独跑必挂、并行跑必挂、失败后无法重跑。需要的共享数据用夹具或工厂现造，用完清理；确实有先后关系的（向导式流程）就合并成一条链路用例。

## 三、框架与封装

### 9. 你的框架分几层？

四层：配置（环境、域名、超时、账号）、客户端（发请求、重试、日志、异常）、接口（按业务域封装具体接口，如 `UserApi.login`）、用例（组织场景与断言）。分层的目的是一处改动只影响一层。

### 10. 为什么重试只对幂等方法开放？

非幂等重试会产生重复副作用：重复下单、重复扣款。POST 要重试必须带幂等键且服务端去重。另外只对 5xx、连接错误和 408/429 重试——408 是请求超时、429 是限流，退避之后有意义；其余 4xx 才是请求本身的问题，重试一百次结果一样。

### 11. 怎么让封装本身可测？

依赖注入。把「真正发请求的函数」作为参数传进客户端，测试时传假实现，就能断言重试次数、异常类型、URL 拼接、头合并，不用起服务。这一层不测，「框架有 bug」和「接口有 bug」就永远分不清。

### 12. 日志该记什么、不该记什么？

记方法、路径、状态码、耗时、重试次数、请求 id；不记 Authorization、Cookie、密码、完整手机号和身份证。响应体只在失败时记，并截断长度（比如 500 字符）。

## 四、数据与执行

### 13. 测试数据从哪来？

三种来源，优先级从高到低：调接口造（最真实，但造数接口本身可能有 bug）、直接写库（快，但绕过业务校验）、固定数据（只适合只读查询）。造数要保证唯一性，否则第二轮就撞 409。

### 14. 数据清理失败怎么办？

清理写在夹具 `yield` 之后并 `try/except` 包住：失败只记警告，不把用例判红——否则清理问题会掩盖业务问题。同时给数据加唯一前缀，方便定期批量清理。

### 15. 并发用例怎么断言？

断言「状态组合」，不断言「谁赢」。比如两个线程同时支付同一订单，结果应该是 `{200, 409}` 这样的集合；断言「第一个一定成功」会因线程调度随机变红。

## 五、报告与 CI

### 16. 报告里最该看什么？

先看失败的用例名和断言消息（是否可判定），再看失败是否集中在某个接口或某个维度，最后看耗时趋势。通过率是结论，不是线索。

### 17. CI 上的偶发失败怎么治理？

先分类：环境（端口未就绪、连接超时）、数据（唯一性冲突、清理失败）、时序（异步未完成）、真 bug。分别用就绪等待、数据隔离、轮询等结果、修 bug 解决；重试只兜环境抖动，治不了时序问题，更不能掩盖真 bug。给不稳定的用例打 `flaky` 标记并限期修。

### 18. 为什么 CI 不该跑依赖外网的用例？

外网不稳定会导致随机失败，外部服务会变更、会限流，还可能涉及密钥。CI 必须可重复、可离线、可并行。要测外部依赖，用 mock 或专门的联调环境，单独一条流水线。

## 六、AI 与接口测试

### 19. AI 生成用例，你怎么保证质量？

三步：先给覆盖矩阵（接口 × 维度），让 AI 按格子填；提示词里写死输出 schema 和硬约束（期望结果必须可判定）；生成后过五道审——可执行、可判定、不重复、前置清楚、数据可造。审完删改多少取决于文档质量（经验值：改动量常在 30%–60%），别当固定比例。

### 20. AI 在接口测试里真正擅长什么？

擅长：从接口文档提取字段和约束、把需求拆成测试点、生成边界组合、把失败日志翻译成人话。不擅长：判断业务规则对不对、决定哪些该自动化、替代人工做最终归因。
