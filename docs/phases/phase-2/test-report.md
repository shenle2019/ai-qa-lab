## 3. 优点

- **状态机集中在 skill 里**：`case.batch` 的 `FLOW` 表就是状态机的唯一定义，REST 层和前端都只是调用方，以后加状态只改一处。
- **列表轻、详情重**：列表接口不返回 steps / expected，编辑时才拉详情，用例量涨上去也不会拖慢列表。
- **生成链路吃到了需求分析**：`requirement_id` 会把 `analysis_json.features` 的名称和验收标准拼进 prompt，生成结果明显更贴合原始需求。
- **跳过原因可读**：批量操作失败不会静默，`skipped[].reason` 直接显示中文原因。

## 4. 已知不足

1. **没有分页**：用例列表一次性返回全部，项目内用例过千会卡。留到 Phase 4 或统一做分页组件时处理。
2. **没有用例导入导出**：目标站的「用例管理」通常配有 Excel 导入，本阶段未做。
3. **生成结果不可逐条取舍**：现在只有「全部提交审核」，不能勾选其中几条入库。目标站是「你决定要不要写入」，这里可以再细一档。
4. **评审人写死为 `local`**：没有接用户体系（Phase 5 才做用户管理）。

## 5. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 大模型返回的步骤不合法 | 生成失败，用户看到 502 | `_normalize_step` 已做兜底校验，错误信息提示「模型没有返回有效用例」 |
| 批量删除没有二次确认的兜底 | 误删不可恢复 | 前端有确认弹窗；后续可加软删除 |
| 用例数量增长后列表变慢 | 体验下降 | Phase 3 之后补分页与索引 |
| 项目间数据隔离靠前端筛选 | 误操作到别的项目 | 后端按 `project_id` 过滤，前端仅做默认选中 |

## 6. 结论

Phase 2 的功能测试模块已经能支撑「需求 → 用例 → 评审」这条主线：生成走 AI、入库要人确认、评审有记录、批量能纠错。接口与 skill 的分层也让后续替换生成引擎（比如换成别的模型或规则引擎）不需要动页面。

**建议进入 Phase 3：知识库。**
