## 1. 概要

Phase 1 把「需求管理」从占位页做成完整链路：上传需求文档 → 抽取文本 → AI 分析出功能清单/界面描述/待澄清项/风险 → 一键生成测试计划（含人天与里程碑）→ 右侧对话 Agent 直接修订分析。全部能力以 skill 形式注册，前端不写死业务逻辑。

## 4. 质量评估

**优点**

- 分析结果结构化程度高：功能清单带优先级与验收标准，待澄清项带「为什么问」，可直接拿去开评审会。
- 计划的人天有自洽校验（用里程碑天数之和校正模型自报值），不会出现「4 个里程碑 3 天」这类矛盾。
- 对话 Agent 会判断「是否真的需要改」，遇到重复条目会拒绝重复添加并说明原因，不是无脑覆盖。
- 上传解析零第三方依赖，换机器不用再折腾 `pypdf` / `python-docx` 的版本冲突。

**不足**

- PDF 只支持文本层，扫描件必须手工粘贴；没有 OCR。
- 分析 JSON 由模型自由生成，字段齐全度随需求质量波动（需求写得糊，`ui` 就容易空）。
- 对话历史只喂最近 12 条，超长会话会丢早期上下文。
- 需求删除是硬删除，附件目录同步清理但无回收站。

## 5. 风险与遗留

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| 扫描版 PDF 无法抽取 | 用户需手工粘贴 | 已在 note 里明确提示；Phase 3 知识库再接 OCR |
| LLM 输出字段缺失 | 前端渲染空块 | `_normalise()` 兜底补空数组，不报错 |
| 长会话上下文截断 | 早期结论被遗忘 | `HISTORY_LIMIT=12`，后续可改为摘要压缩 |
| 硬删除 | 误删不可恢复 | Phase 5 加软删除与回收站 |
| 附件存本地磁盘 | 多实例部署不共享 | 与知识库一并迁移到对象存储（可选） |

## 6. 结论

需求管理模块的功能完整度、结构化程度与交互形态均达到目标站水平，测试覆盖到接口层与真实模型端到端，未发现阻断性问题。**准予进入 Phase 2（功能测试 / 用例管理）**。
