## 3. 优点

- **分块可解释**：段落优先 + 固定窗口兜底，块边界能对应回原文，出问题好定位。
- **检索接口形状稳定**：现在词面、以后向量，`hits` 与 `context` 的字段不用改，页面与下游 Agent 都不用动。
- **`context` 一步到位**：检索结果直接拼成 `[文件#序号] 片段`，生成类 skill 拿到就能塞进 prompt，省掉每处重复拼装。
- **统计内联**：`kb.list` 直接返回文档数与分块数，页面不用发 N+1 个请求。

## 4. 已知不足

1. **没有向量检索**：同义词、近义表达召回不到（问「下载」找不到写「导出」的段落）。等 Phase 5 的向量模型管理。
2. **分块参数改了不重切**：历史文档保持旧分块，需要手动重建。可以在后续加「重新分块」按钮。
3. **没有文档版本/更新**：同名文档重复上传会变成两条，不会覆盖。
4. **PDF 提取依赖文本层**：扫描件会返回「未能提取到文本」提示，没有 OCR。
5. **检索无 rerank**：top_k 里靠后的块质量不稳定，接 LLM 时应只取前 3 条。

## 5. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 超大文档一次入库卡住请求 | 上传接口超时 | 目前限 20MB；后续可改后台任务分块 |
| 中文二元组切分召回噪声 | 命中不相关块 | 已用原句命中加成压制；接 LLM 时限制 top_k |
| 知识库与项目解耦不彻底 | 跨项目串资料 | `project_id` 已落库，页面按项目过滤留到 Phase 4 统一处理 |
| 分块正文全量存 SQLite | 库体积增长快 | 现阶段文档量小可接受；后续可只存偏移量与原文路径 |

## 6. 结论

知识库这一层把「资料」变成了平台可调用的能力：上传即分块、分块可查看、检索有片段和分数、`context` 可直接进 prompt。它是后面接口自动化和 UI 自动化生成用例的上下文来源。

**建议进入 Phase 4：接口自动化。**
