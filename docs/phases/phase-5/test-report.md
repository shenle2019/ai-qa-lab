## 4. 优点

1. **同一份步骤两种用法**：页面执行与脚本导出共用 `steps_json`，导出脚本能直接进 CI，没有「平台里能跑、拿出去不能跑」的割裂。
2. **快照驱动的生成**：`snapshot()` 只喂 80 个节点、每节点 6 个属性，token 可控又能让模型挑到稳定选择器；比纯「根据 URL 猜」可靠得多。
3. **失败可回溯**：每一步的状态、错误文案、截图都在一条记录里，AI 归因和人工排查看同一个地方。
4. **分类而非堆砌**：系统 AI 用 `kind` 分类后，`resolve_model()` 只会挑 chat 模型，避免「配了 embedding 却被当大模型用」。

## 5. 不足

1. **没有套件**：只能一条一条跑，不能「一组用例顺序执行 + 汇总报告」，这是与目标站最明显的差距。
2. **没有录制**：目标站的「录制」是点一遍生成步骤，当前只能 AI 探索或手写 JSON。
3. **视觉识别未接执行**：Midscene 只是模型登记，没有「选择器失效 → 截图让视觉模型定位」的降级链路。
4. **无并发**：执行是同步阻塞的，一条用例跑 1–2 秒，10 条就要十几秒，没有并行与队列。
5. **选择器不稳**：AI 生成的 `text=试检索` 这类中文文本定位在改文案后会失效，`assert_text body` 也偏宽。
6. **无鉴权隔离**：用户管理只是目录，任何能访问平台的人都能改数据。

## 6. 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Playwright 浏览器体积大（~150 MB） | 换机器要重装 | 已固定到 `E:\...\.pw-browsers`，`ui_runner` 内置 `PLAYWRIGHT_BROWSERS_PATH` 兜底 |
| 同步执行受 HTTP 超时限制 | 长用例会 504 | 前端超时已放到 180 s；后续应改成任务队列 |
| AI 生成步骤可能越权操作 | 在真实系统上点错按钮 | 目前只对本地 SUT 跑；接生产前需要「只读账号 + 域名白名单」 |
| 截图落盘无限增长 | 磁盘 | `data/ui-shots` 目前不清理，后续按保留天数清理 |

## 7. 下一阶段建议

1. **UI 套件**：`ui_suites` + 顺序执行 + 汇总（通过率、失败步骤、耗时），对齐目标站第 4 个 Tab。
2. **录制**：用 Playwright codegen 或 CDP 事件流生成 `steps_json`。
3. **失败降级**：选择器找不到时截图 → 视觉模型给候选元素 → 重试一次。
4. **异步执行**：BackgroundTasks/队列 + 前端轮询，避免长用例超时。
