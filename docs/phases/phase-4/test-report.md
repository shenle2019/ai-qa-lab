## 优点

1. **断言是真断言**。执行器发真请求、按 `status`/`contains`/`json_path` 判定，没有把「跑通」定义成「代码没抛异常」。
2. **失败信息可读**。变量缺失、Base URL 缺失、状态码不符都有中文原因，直接显示在步骤行上。
3. **生成质量靠上下文**。把接口的响应字段一起喂给模型后，`extract` 从错误的 `data.id` 变成正确的 `id`，一次生成的可执行率明显提高。
4. **归因有边界**。提示词要求「一句结论 + 引用字段作依据 + 一条修复建议」，输出能落到「断言错 / 用例错 / 服务端缺陷」三选一，不是泛泛而谈。

## 不足

1. **无并发执行**。用例逐条跑，几十条场景会慢。
2. **无环境变量集**。Base URL 只能手填或从资产回退，没有「开发/测试/预发」多环境切换。
3. **无断言模板库**。模型偶尔写出 SUT 不支持的断言（如给无鉴权接口写 401），只能靠归因事后发现。
4. **无定时任务**。不能配「每天跑一遍回归」。
5. **场景无分支/循环**。只支持线性步骤。
6. **请求体不支持文件上传**。multipart 接口只能手工调试。

## 风险

1. 模型生成的用例必须人工过一遍再启用，否则会把「模型臆想的契约」当缺陷。
2. 执行器能发任意请求（含内网地址），部署到共享环境需要加目标白名单。
3. `api_runs.steps_json` 每步都存完整响应，跑几千次后表会变大，需要归档策略。
4. AI 归因会消耗 token，失败多的时候成本可见，需要限流或按需触发。
