## F1 只读功能被写鉴权拦住，提示方式还不统一

**现象**
- 知识库问答和首页“知识库快问”本质是只读查询，但接口是 POST，未持密钥时返回 401，页面直接跳到 `#/login`，问题内容不保留，登录页也没有任何“为什么被带到这里”的说明。
- 知识库页面自己写着“只读浏览不需要密钥”，与实际行为矛盾。
- API 工作台的发送/运行全部同样是只读请求，却走另一套错误处理：页面内出现英文 `unauthorized`，不跳转、无中文指引。

**复现步骤**
1. 打开 `#/knowledge`，输入“工单如何升级优先级？”，点“提交问题”。
2. 结果：跳转 `#/login`，输入框丢失，无提示。
3. 打开 `#/workbench`，直接点“发送”。
4. 结果：页面内出现 `unauthorized`（英文），URL 不变。

**判断**：异常。核心只读能力对首次访客不可用；同一系统两种 401 表现，说明缺少统一的鉴权错误处理。

**证据**：`screenshots/040-knowledge-submit-no-key.png`、`screenshots/041-dashboard-kb-no-key.png`、`screenshots/053-workbench-error-text.png`

## F2 访问密钥保存/校验没有真实反馈

**现象**
- 空密钥点“保存”：提示“已保存，正在返回首页…”，实际 localStorage 里没有 key；用户以为已登录，下一次写操作又被踢回来。
- 纯空格同样被当作保存成功。
- 错误密钥：只在提交写操作时暴露，表现为静默清除 key + 跳转登录页，没有“密钥错误/鉴权失败”提示。
- 5000 个字符的密钥也直接保存，没有长度/格式校验或“验证密钥”按钮。

**复现步骤**
1. 打开 `#/login`，不填内容点“保存” → 返回首页，`localStorage.sut_api_key` 为空。
2. 填入 `wrong-key-123` 保存；回工单页新建并提交 → 跳到登录页，key 已被清空，无错误文案。

**判断**：异常。密钥是写操作唯一入口，却缺少最基本的有效性反馈，用户只能靠试错。

**证据**：`screenshots/030-login-save-empty.png`、`screenshots/032-fake-key-create.png`、`screenshots/077-login-long-key.png`

## F3 401 打断表单：内容全丢，且不解释原因

**现象**
- 工单新建/编辑、模型保存等表单，填完提交遇到 401 时，先跳转 `#/login`，组件被卸载，已填内容全部丢失。
- 登录页只有静态说明，没有“你刚才的操作被拒绝，因为需要密钥”的上下文。
- 从登录页点浏览器返回，回到的是空页面状态（弹窗和内容都没了）。

**复现步骤**
1. `#/tickets` → 新建工单 → 填标题“探索测试请勿创建” → 创建。
2. 结果：跳到 `#/login`，标题输入丢失；`history.back()` 回到工单页，弹窗未恢复。

**判断**：异常。表单越复杂，损失越大；至少要保留草稿或把错误原因带到登录页。

**证据**：`screenshots/021-ticket-create-no-key.png`、`screenshots/091-back-after-401.png`

## F4 测试平台四个表单：必填为空时“点了没反应”

**现象**

**复现步骤**

2. 结果：无请求、无提示、无任何变化。

**判断**：异常。新用户会认为按钮坏了或系统卡了。

**证据**：`screenshots/060-platform-empty-project.png`（源码 `Platform.vue` 的 `createProject/createCase/createPlan/createDefect` 提前 return）

## F5 行内状态下拉：一改即存，无确认无撤销

**现象**
- 工单列表每行的优先级/状态下拉在 `change` 时直接 PATCH，没有保存按钮、没有成功提示、没有撤销。
- 两个下拉都没有 `title`/`aria-label`，只看得到“低/中/高”，不知道这一列代表什么；状态还在操作列重复显示一枚徽章。
- 未持密钥时误触：弹原生 `alert`，随后被踢到登录页（实测）。

**复现步骤**
1. `#/tickets`，点第一行优先级下拉改成“低”。
2. 无密钥环境：出现 alert“需要访问密钥…”，跳转 `#/login`；有密钥环境：立即保存，无二次确认。

**判断**：疑似风险（源码确认行为，未在有密钥环境执行写入）。浏览时误触就会改数据，是这类后台最容易踩的坑。

**证据**：`screenshots/033-row-select-no-key.png`、`screenshots/076-ticket-row-selects.png`（源码 `Tickets.vue#changeStatus/changePriority`）

## 本轮盲区（Agent 探索测不到的）

- 有密钥后的真实写入行为（重复提交、并发修改、删除后列表一致性）——本次按硬约束未执行。
- 业务正确性：通过率、token 统计、计划执行结果是否算对，需要断言和业务知识。
- 真实用户感受：高频运营场景下的操作成本、移动端单手可达性。
- 权限边界：同一密钥是否有粒度区分（本次只有一个共享密钥）。

## 方法论局限（诚实记录）

- 脚本用的是 DOM `el.click()`，可以点到被遮罩挡住或真实用户点不到的元素；因此“能点到”不等于“用户能点到”。本轮只把这类点击当作观察入口，不作为缺陷证据。
- 首轮脚手架在同一个 hash 路由间跳转不会重载 SPA，导致弹窗状态串场；已改为每个场景强制新文档后重跑，废弃了首轮 8 条记录。
- 有 3 条记录因为探测参数写错（状态值、分类按钮文本、JS 赋值绕过 maxlength）判定为无效，未计入发现。
