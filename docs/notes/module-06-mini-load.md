# 模块 06 笔记：压测不是“跑一下”，是拿数据做判断

## 问题

性能测试最容易写成“我跑了 100 个并发，没报错”。这不算结论。

真正要回答的是：吞吐多少、P95 多少、错误率多少、有没有超过阈值。

## 方案

包放在 `libs/miniload`，只用 Python 标准库 + requests。

| 能力 | 实现 |
|---|---|
| 并发 | 每个 VU 一个线程 |
| 阶梯启动 | 按 VU 序号错开启动时间 |
| 延迟采集 | `time.perf_counter()` |
| 百分位 | 排序后取 P50/P90/P95/P99 |
| RPS | 总请求 / 实际耗时 |
| 错误率 | 失败数 / 总数 |
| 阈值 | P95、错误率、最小 RPS |
| 报告 | JSON + 离线 HTML + 柱状分布 |

## 结果

- 5 个框架元测试通过
- SUT `/health`：8239 次请求，1371.2 RPS，P95 21.11ms，错误率 0.00%，PASS
- 报告：`docs/portfolio/module-06-load-report.html`

## 踩坑

1. 本机压测先打满自己，1371 RPS 不代表服务端极限。
2. 平均延迟会骗人，必须看 P95/P99。
3. HTTP 错误和网络异常都算失败，但要分开记。
4. ramp-up 要算进总时长。
5. HTML 报告必须离线，不依赖 CDN。

## 一句话

压测的价值不在“跑了多少”，在“跑完以后能不能用数据说清楚：能不能上线”。
